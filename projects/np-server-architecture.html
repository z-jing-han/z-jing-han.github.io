Remote Working Ground Server · Architecture

Two concurrency models, one shell server

A multi-client shell interpreter is served two different ways: a single process multiplexing every client with select(), and a process-per-client design where independent processes coordinate through POSIX shared memory and signals instead of one shared address space.

C++ · Sockets · POSIX IPC Spring 2025

In short

np_single_proc.cpp and np_multi_proc.cpp put one shell interpreter behind two different server designs: a single process multiplexing every client with select(), and a process-per-client design synchronized through POSIX shared memory and signals.

This page covers what the project-card bullets don't have room for: how np_single_proc.cpp's in-process map hands one client's output to another, and how np_multi_proc.cpp rebuilds that same hand-off once every client is its own OS process.

01 · Single Process with Select

One process, serving every client

select() reports which connected client socket has a line waiting. The process has exactly one stdin, one stdout and one set of environment variables, so it borrows them for whichever client is ready, handles one line, and gives them back before asking select() again — no fork(), no second process, ever. 

// np_single_proc.cpp:94-96, 106 — save stdio once, select() every cycle
dup2(STDIN_FILENO, 4);
dup2(STDOUT_FILENO, 5);
dup2(STDERR_FILENO, 6);
/* ... */
select(max_fd_history+1, &rset, NULL, NULL, (struct timeval *)0);
// np_single_proc.cpp:202-219 — borrow stdio for one client, one line
if (FD_ISSET(client_fd_table[i], &rset)) {
    clearenv();
    for (auto env : User_Info_Map[i].EnvVar)
        setenv(env.first.c_str(), env.second.c_str(), 1);

    dup2Client(client_fd_table[i]);                 // borrow stdio
    npshell_handle_one_line(User_Info_Map, i, &exit, client_fd_table, firewall);

    dup2(4, STDIN_FILENO);                          // give it back
    dup2(5, STDOUT_FILENO);
    dup2(6, STDERR_FILENO);
}
The cost of this design: because every client's turn runs to completion inside the same one process, nothing else can happen — including servicing another client's socket — until npshell_handle_one_line() returns. A command that can't finish quickly stalls every other connected client, not just its own.

That single address space is also what makes cross-user pipes simple here: forwarding Client 1's output to Client 2 is just an ordinary map this one process already owns.

02 · Multi-Process with Shared Memory

One process per client, joined by shared memory

Going back to a process per client buys back OS-level isolation, but a forked process doesn't inherit a live view of who else is connected. Everything that used to be a variable in one process — the connection table, the broadcast buffer, the pipe between two users — now has to live somewhere every process can reach. 

// np_multi_proc.cpp:76-105 — four segments replacing one process's private state
UserInfo_fd        = shm_open("UserInfo", O_CREAT | O_RDWR, 0666);   // connection table, incl. each user's pid
MSG_fd              = shm_open("msg", O_CREAT | O_RDWR, 0666);        // broadcast message buffer
UserPipeMatrix_fd   = shm_open("UserPipeMatrix", O_CREAT | O_RDWR, 0666); // per-pair pipe status
Firewall_fd[i]      = shm_open(("firewall[" + to_string(i) + "]").c_str(), O_CREAT | O_RDWR, 0666);
