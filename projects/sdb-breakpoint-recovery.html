Single Instruction Debugger · Design

Why breakpoints can't restore themselves immediately

A ptrace-based breakpoint works by overwriting one byte of the target program with 0xCC, then putting the original byte back before that instruction ever really runs. Getting the timing of that swap right — exactly one instruction removed, then reinserted, no matter what kind of instruction it is — turned out to be the hardest part of the whole debugger.

C++ · ptrace · Capstone todo/sdb.cpp Spring 2025

In short

sdb.cpp is a from-scratch, instruction-level debugger for x86-64 Linux binaries — static, dynamically linked, or PIE — built directly on ptrace and /proc/[pid]/{mem,maps,auxv}, with disassembly via Capstone.

This page covers what the project-card bullets don't have room for: a breakpoint design that had to be rebuilt after its first version couldn't reliably resume through jump-type instructions, and the dispatch protocol that keeps single-step, continue, and syscall-tracing consistent around it.

01 · Mechanism

A trap byte that has to disappear, then reappear

Setting a breakpoint means writing 0xCC (int3) over the first byte of an instruction. When the CPU reaches it, it traps into the kernel and ptrace reports a stop — but the instruction that was supposed to run is now gone from memory. Every command that resumes the target has to put it back first, and every breakpoint that's still meant to fire has to be re-armed afterward.

A hit is detected by rewinding $rip by one: after an int3 traps, the CPU has already advanced past it, so the byte it actually executed sits at $rip - 1. sdb checks that address against the breakpoint table before falling back to checking $rip itself, for the case where a breakpoint was set exactly where execution already sits and hasn't been stepped over yet. 

// sdb.cpp:24-32
struct breakInfo {
    vector<int> num;          // every user-visible ID sharing this address
    unsigned char originalByte;
    bool active;               // still installed, or just kept for bookkeeping
    bool hit;                  // currently sitting with the trap byte removed
};

constexpr unsigned char INT3 = 0xcc;
map<unsigned long, struct breakInfo> breakInfoMap;

Keyed by address rather than by breakpoint ID, so two IDs set on the same instruction share one trap byte and one hit/active state — deleting one leaves the address, and the other ID, untouched.

02 · The redesign

Restoring immediately breaks resuming through a jump

The first version of the breakpoint logic restored the original byte the moment a breakpoint was hit, and only reinserted 0xCC once control flow had been handled. It worked for straight-line code, but a jump, call, or branch sends execution somewhere that isn't just "the next byte" — so restoring early meant guessing, at every place execution could resume, whether a trap byte was still owed wherever it landed.

In the current design, hitting a breakpoint only sets a flag; the restore-step-rearm sequence itself lives in exactly one function, run whenever the next si, cont, or syscall command would resume the target anyway: 

// sdb.cpp:55-86 — recovery_oneStep_restore()
int recovery_oneStep_restore(int child) {
    unsigned long addr = 0x0;
    for (auto breakPoints: breakInfoMap)
        if (breakPoints.second.hit)
            addr = breakPoints.first;
    if (!addr) return 1;               // nothing pending — no-op

    poke_byte(child, addr, breakInfoMap[addr].originalByte);   // put it back
    ptrace(PTRACE_SINGLESTEP, child, 0, 0);                    // exactly one instruction

    if (waitpid(child, &status, 0) > 0 && WIFSTOPPED(status))
        if (breakInfoMap[addr].active)
            poke_byte(child, addr, INT3);                      // re-arm, if still installed
    breakInfoMap[addr].hit = false;

    if (WIFEXITED(status)) { /* report termination, exit */ }
    return 0;
}

hit and active answer two different questions: hit means "a trap byte is currently missing here and owes a restore," active means "the user still wants a breakpoint here." A deleted breakpoint that was already hit still needs the single-step to get past it — it just doesn't get 0xCC written back afterward.

The address-keyed table pays off again here: every caller of recovery_oneStep_restore() — whether the user typed si, cont, or syscall — runs the exact same sequence, because the function doesn't need to know what instruction is under the breakpoint, only that one is currently sitting with its trap byte removed.

03 · Control flow

One dispatch loop, three ways a command can leave it

Some commands change nothing about the target's execution state (break, patch, info); some resume it and need a fresh waitpid() to see what happened (cont); and some resume it and already know the outcome, because they had to call waitpid() themselves to find out (syscall, or si stepping past a just-hit breakpoint). The dispatch loop needs to treat those three cases differently, so every command handler returns which one applies.

ReturnMeaningExample
0Nothing resumed — loop back for another command immediatelyinfo, break, patch
1Resumed, but not yet waited on — the outer loop's own waitpid() handles itcont, or si with no pending breakpoint
2Already resumed and waited on internally — skip straight to the per-stop bookkeepingsyscall hitting a breakpoint, or si stepping past one

The si handler is where this pays off most directly: if recovery_oneStep_restore() finds a pending breakpoint, its single step is the instruction the user asked to execute, so si skips issuing a second one and returns straight to the caller. If there was nothing pending, it issues its own step and lets the outer loop wait on it like normal. 

// sdb.cpp:312-322
} else if (command_list[0] == "si") {
    if (!recovery_oneStep_restore(child))
        return 2;                                   // recovery's step already covered it
    ptrace(PTRACE_SINGLESTEP, child, 0, 0);
    return 1;
} else if (command_list[0] == "cont") {
    recovery_oneStep_restore(child);
    ptrace(PTRACE_CONT, child, 0, 0);
    return 1;
}

syscall goes further still: because catching an enter/leave event already requires its own waitpid() and its own disassembly, it does that work inline and returns 0 on a normal syscall stop — unless the stop turns out to be a breakpoint instead of a syscall, in which case it hands back 2 so the outer loop's breakpoint bookkeeping runs once, not twice.
