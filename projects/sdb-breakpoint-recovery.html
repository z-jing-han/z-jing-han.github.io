Single Instruction Debugger · Design

Breakpoint handling in sdb

sdb is an instruction-level debugger for x86-64 Linux, built on ptrace with Capstone for disassembly. The hardest part was restoring and re-inserting the 0xCC byte at the right time. My first design did not consider breakpoints on jump instructions, so I rewrote it.

C++ · ptrace · Capstone Spring 2025 · refactored Sep 2026

In short

sdb supports load, si, cont, info reg, info break, break, breakrva, delete, patch and syscall, on static, dynamically linked and PIE binaries. The process setup and the memory-map reader (ptools.cpp) come from the course examples. This page covers the breakpoint design and how the command loop knows when to call waitpid().

How a breakpoint works

A breakpoint replaces the first byte of an instruction with 0xCC (int3). When the CPU executes it, the process stops with rip one byte past the breakpoint. sdb checks whether rip - 1 is a breakpoint address and, if so, moves rip back by one. It also checks rip itself, for a breakpoint set at the address where the program is already stopped. 

// sdb.cpp:24-32
struct breakInfo {
    vector<int> num;          // breakpoint IDs at this address
    unsigned char originalByte;
    bool active;               // false only for the entry-point stop (ID -1)
    bool hit;                  // stopped here; step over before resuming
};

constexpr unsigned char INT3 = 0xcc;
map<unsigned long, struct breakInfo> breakInfoMap;

The table is keyed by address, so several breakpoint IDs on the same instruction share one saved byte. Deleting one ID leaves the others in place. Deleting the last one writes the original byte back and removes the entry.

Why the original byte is restored later

In my first version, I restored the original byte as soon as a breakpoint was hit and put 0xCC back after handling the next command. That works for straight-line code. After a jump or call, however, the next instruction is not at the next address, so several places in the code had to work out where and when to re-insert the byte. The code became hard to follow, and it failed on test programs with breakpoints on jump instructions.

The restore sequence is in one function, called by si, cont and syscall. A single step always stops after exactly one instruction, whether that instruction jumps or not, so the byte can be re-inserted safely. 

// sdb.cpp:55-86, simplified
int recovery_oneStep_restore(int child) {
    unsigned long addr = 0x0;
    for (auto breakPoints: breakInfoMap)
        if (breakPoints.second.hit)
            addr = breakPoints.first;
    if (!addr) return 1;               // no breakpoint to step over

    poke_byte(child, addr, breakInfoMap[addr].originalByte);   // restore
    ptrace(PTRACE_SINGLESTEP, child, 0, 0);                    // one instruction

    if (waitpid(child, &status, 0) > 0 && WIFSTOPPED(status))
        if (breakInfoMap[addr].active)
            poke_byte(child, addr, INT3);                      // re-insert
    breakInfoMap[addr].hit = false;

    if (WIFEXITED(status)) { /* report termination, exit */ }
    return 0;
}

hit means the program is stopped on this breakpoint and has to step over it before resuming. active means the byte should be re-inserted afterwards. The only inactive entry is the breakpoint sdb sets on the program's entry point (ID −1) so that it stops there after load. It is stepped over like the others, but never listed or re-inserted.

When to call waitpid()

Each command is run by exeSDBcommand(). After a command resumes the target, the main loop calls waitpid(), checks for a breakpoint hit, and disassembles the next five instructions. Some commands have already called waitpid() themselves, and a second call would block. So exeSDBcommand() returns one of three values that tell the main loop what is left to do:

Return valueMeaningExample
0Nothing to wait for. Read the next command.info, break, patch, delete, or syscall stopping at a system call
1Target resumed but not waited on. The main loop calls waitpid().cont, or si with no breakpoint to step over
2Target resumed and already waited on. The main loop skips waitpid() and checks for a breakpoint.si over a hit breakpoint, or syscall stopping at a breakpoint

For si, if a breakpoint was pending, the single step inside recovery_oneStep_restore() is already the step the user asked for, so si returns 2 without stepping again: 

// sdb.cpp:312-322
} else if (command_list[0] == "si") {
    if (!recovery_oneStep_restore(child))
        return 2;                         // already stepped and waited
    ptrace(PTRACE_SINGLESTEP, child, 0, 0);
    return 1;
} else if (command_list[0] == "cont") {
    recovery_oneStep_restore(child);
    ptrace(PTRACE_CONT, child, 0, 0);
    return 1;
}

syscall calls waitpid() itself to find out whether the target stopped at a system call or at a breakpoint. For a system call it prints the syscall number and return value and returns 0. For a breakpoint it returns 2, so the main loop reports the hit.

PIE and dynamically linked programs

sdb reads the entry point from AT_ENTRY in /proc/[pid]/auxv. For a dynamically linked program this is the program's own entry point, not the dynamic linker's, so a breakpoint there stops after the loader has finished. For breakrva, the load base is the start of the first mapping in /proc/[pid]/maps whose name matches the file that /proc/[pid]/exe points to. This also works when the program is started through a symbolic link.
