xv6-riscv · Deep dive

Refactoring the physical memory allocator

Merging five xv6 kernel labs into one kernel put two features on a collision course inside a single file: superpages, from the page-table lab, and copy-on-write fork, from the COW lab. Both of them want to own the life cycle of a physical frame. This is the allocator I rebuilt so that they could share it.

C · RISC-V (Sv39) kernel/kalloc.c, kernel/vm.c Aug 2026 MIT 6.1810, self-study

In short

Stock xv6 hands out one 4KB page at a time from a single global freelist, with no notion of a frame being shared. Superpages need the allocator to hand out 2MB blocks and to take them back; copy-on-write needs every frame to carry a reference count so a shared page is freed exactly once, at either granularity.

I replaced the two separate allocators with one structure behind one lock that tracks both page sizes and all reference counts together, so splitting a superpage into 512 pages and coalescing them back are atomic operations rather than a check-then-act race. Two bridging calls, ksplit() and kaddrefcnt(), let the page-table code share and demote frames without the allocator's books ever going out of sync.

01 · The problem

Two labs, one file, incompatible assumptions

Each lab was developed on its own branch and passed its own test suite. The conflict only appeared at merge time, because both branches had quietly taken ownership of the same thing: who decides when a physical frame is free.

The page-table lab adds superpages: a single page-table entry maps a 2MB region instead of 512 separate entries, which cuts page-table memory and TLB pressure on workloads that touch a lot of memory at once — a large sbrk(), for example. The COW lab adds copy-on-write fork: parent and child share the same physical frames, read-only, until one of them writes and forces a real copy, instead of eagerly duplicating the whole address space on every fork().

Put together, every frame now needs a reference count at either granularity, and the two granularities need to convert into each other without ever losing track of a frame that is still mapped somewhere. The obvious way to get there — keep the lab's two allocators side by side, each behind its own lock, and bolt a refcount[] array onto whichever one COW happens to touch — breaks in two specific ways.

Failure mode 1: splitting is one-way, so the superpage pool only shrinks

When the 4KB freelist runs dry, the allocator has to break a 2MB superpage into 512 pages to keep serving requests. If nothing ever puts those pages back together, the supply of superpages decreases monotonically over the system's lifetime. Eventually superalloc() fails even though 2MB of contiguous memory is sitting free, just in 512 pieces.

Failure mode 2: a check-then-act race across two locks

"Is the 4KB freelist empty?" and "split a superpage to refill it" are two separate critical sections if the two pools live behind two locks. Two CPUs can both observe empty at the same moment and each split a different superpage when one split would have been enough — and nothing stops them from racing on which superpage that is. That is a correctness hazard on a multi-core kernel, not just wasted memory.

Coalescing makes this worse: it needs to inspect a freelist and 512 reference counts as one atomic fact. Split across two independently-locked structures, there is no moment at which that fact is stable.

02 · The design

One structure, one lock, two granularities

Both page sizes and every reference count live in one struct, guarded by one lock. Everything that has to change together is now reachable from inside a single critical section. 

// kernel/kalloc.c
struct {
  struct spinlock lock;       // protects every field below
  struct run *freelist;       // free 4KB pages
  struct run *freelist_super; // free 2MB superpages
  int refcount[NPAGE];        // refcount[PGIDX(pa)] = live references to pa
  int free_in_group[NGROUP];  // how many of a group's 512 sub-pages are free
} kmem;

With PHYSTOP at 128MB that is NPAGE = 32,768 tracked frames across NGROUP = 64 superpage-aligned groups.

Four decisions worth defending

One lock, deliberately — for now

Refcount decrements, freelist membership and the coalescing counters all have to change together, and coalescing touches both freelists at once. Two locks would need a consistent ordering discipline at every joint site. Trading multi-core throughput for a design that is obviously correct was the right call at this stage; it is recorded as known debt, not overlooked.

A doubly-linked freelist

Coalescing has to pull one specific page out of the 4KB freelist by address, not from the head. Singly linked, finding the predecessor is an O(n) scan; adding a prev pointer to struct run makes each removal O(1), so reclaiming a whole group is 512 constant-time unlinks.

Exactly two sizes, not a general buddy system

xv6 only ever needs 4KB or 2MB, so split_locked() and coalesce_locked() are one-shot, non-recursive operations rather than a general order-0..9 split/merge tree. The generality would have been unused complexity in exchange for harder-to-verify code.

Uniform reference counting

kalloc() and superalloc() both set a frame's count to 1; kfree() and superfree() both decrement and only push the frame back onto a freelist at zero. Freeing and unsharing become the same operation, which is exactly the hook COW needs — and it works identically at both sizes.

Cheap invariants make the structure defend itself: coalesce_locked() panics if any page in the group still has a live reference, kfree() panics on refcount underflow, and free_in_group is bounds-checked in both directions. Neither of the two bugs that later took the longest to find tripped any of them — and that was exactly their value: ruling this code out cheaply is what made it reasonable to go looking elsewhere.

03 · The interface

Two bridges into the page-table code

A stock allocator only needs kalloc() and kfree(). Sharing and demoting frames are things vm.c does to a frame the allocator has already handed out, so each one needs an explicit hook. 

// Bump the reference count of an already-allocated 4KB or 2MB frame.
// Call it wherever a mapping starts sharing an existing frame
// instead of calling kalloc() for a fresh copy.
void kaddrefcnt(void *pa);

// An already-allocated superpage at pa is being demoted in place into
// 512 individually-addressable 4KB pages. Call it from vm.c's
// splitpage() right before the PTEs are rewritten.
void ksplit(void *pa);

ksplit() is the interesting one, and it exists because of a real bug. vm.c's splitpage() demotes an in-use superpage by rewriting page-table entries directly — it reads the PTE, clears it, and re-maps the same physical range with mappages(..., 0) at 4KB granularity. It never calls back into the allocator at all.

Without ksplit(), kalloc.c has no idea those 511 new sub-pages now exist: their reference counts are still sitting at their initial 0, so the first kfree() against any of them trips the underflow panic. The general lesson generalises past this one call site: any path that reaches around the public API to change a frame's representation has to be found and given an explicit hook, or the allocator's books silently stop describing reality.

Also worth noting: the user-visible half of this work is a sbrk interface with two independent flag bits — SBRK_LAZY (allocate on fault instead of up front) and SBRK_SUPER (back the region with 2MB superpages) — so a program can ask for eager/lazy and normal/super in any combination.

04 · Copy-on-write

What reference counting buys at the fault handler

With counts in place, fork() stops copying page contents at all, and the write-fault handler gets a fast path that allocates nothing.

uvmcopy() now shares the parent's frame with the child, clears the write bit, and records the original writability in a spare PTE bit (PTE_RSW) so a later fault can tell "this was writable, it is COW" apart from "this was always read-only": 

// kernel/vm.c — uvmcopy(), on fork()
if(*pte & PTE_W)
  *pte = (*pte & ~PTE_W) | PTE_RSW;
*new_pte = *pte;
kaddrefcnt((void *)PTE2PA(*pte));

05 · Limits

Known trade-offs, left deliberately

  • A single global kmem.lock. Correctness over multi-core throughput at this stage. The natural next step is per-CPU free lists, with the global lock reserved for the shared superpage pool and cross-CPU coalescing — out of scope here, and recorded rather than discovered later.
  • uvmunmap()'s trimming prunes only level-0 tables. With PHYSTOP at 128MB this is never exercised: a single process would have to span more than 1GB — 512 level-0 tables — before level-1 pruning mattered. It is a real gap if PHYSTOP or the stress workload grows. That trimming exists at all because of a leak that turned out to be a measurement error.
  • Coalescing is eager. A group is reassembled the instant its 512th page is freed, which costs 512 O(1) unlinks in the freeing path. That is the wrong trade if a workload repeatedly frees and re-allocates across one group boundary; a hysteresis threshold would fix it, and there is no evidence yet that it is needed.
