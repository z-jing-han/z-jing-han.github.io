Rebuilding the physical memory allocator

After the merge, superpages (from the page-table lab) and copy-on-write fork (from the COW lab) both needed to decide when a physical page is freed. This page describes the allocator I wrote so that both features could use it.

kernel/kalloc.c, kernel/vm.c Aug 2026

In short

Stock xv6 keeps one free list of 4KB pages and has no reference counts. Superpages need the allocator to hand out and take back 2MB blocks. COW needs a reference count on every page, at either size. I replaced the two separate allocators with one structure protected by one lock. It holds both free lists, all reference counts, and a free-page counter for each 2MB group, so splitting a superpage into 512 pages and merging them back both happen inside one critical section.

The problem

Each lab worked correctly on its own branch. The page-table lab had a separate superpage pool, and the COW lab added a reference-count array to the normal allocator. Keeping both allocators, each with its own lock, had two problems.

Superpages were never merged back

When the 4KB list is empty, the allocator splits a superpage into 512 pages. Without a way to merge them back, the number of superpages only goes down. After enough 4KB allocations, superalloc() fails even though whole 2MB regions are free.

Checking and splitting were not atomic

With two locks, checking that the 4KB list is empty and splitting a superpage are two separate critical sections. Two CPUs can both see an empty list and both split a superpage. Merging pages back is harder still, because it needs to look at a free list and 512 reference counts at the same time.

The design

All free lists, reference counts and group counters are in one struct, protected by one lock. 

// kernel/kalloc.c
struct {
  struct spinlock lock;       // protects every field below
  struct run *freelist;       // free 4KB pages
  struct run *freelist_super; // free 2MB superpages
  int refcount[NPAGE];        // refcount[PGIDX(pa)] = references to pa
  int free_in_group[NGROUP];  // free 4KB pages in each 2MB group
} kmem;

With PHYSTOP at 128MB, that is 32,768 reference counts and 64 superpage groups.

Design decisions

One global lock

Reference counts, free lists and group counters have to change together, and coalescing touches both free lists. With several locks, I would need a fixed lock order everywhere they meet. I chose one lock because it is easier to verify, knowing that it limits multi-core performance.

Doubly linked free list

Coalescing has to remove specific pages from the middle of the 4KB list. I added a prev pointer to struct run, so each removal is O(1) instead of a scan through the list.

Only two page sizes

xv6 only uses 4KB and 2MB pages, so splitting and coalescing are single steps. A general buddy system with many block sizes would add code that nothing uses.

The same reference counting for both sizes

kalloc() and superalloc() set the count to 1. kfree() and superfree() decrement it and only return the page to a free list at zero. Dropping a shared reference and freeing a page become the same call, which is what COW needs. kfree() releases the lock between the decrement and the list insert so that the junk fill runs outside the lock. This is safe because no other code path can reach a page whose count is 0 before it is on a list.

The allocator also checks its own state. It panics on a reference-count underflow, if a page in a group being coalesced still has references, or if free_in_group goes out of range. None of these checks fired during the later debugging, which let me rule out the allocator quickly.

Hooks for the page-table code

Besides kalloc() and kfree(), vm.c needs two more calls into the allocator. 

// Increment the count of an allocated 4KB or 2MB page.
// Called when a new mapping shares an existing page.
void kaddrefcnt(void *pa);

// A mapped superpage at pa is being split into 512 4KB pages.
// Called from splitpage() in vm.c before the PTEs are rewritten.
void ksplit(void *pa);

I added ksplit() because of a bug. splitpage() turns a mapped superpage into 512 4KB mappings by rewriting the PTEs directly, without calling the allocator. The allocator still had a count of 0 for the other 511 pages, so the first kfree() on any of them panicked with a reference-count underflow. Any code that changes a page's size outside the allocator has to report it to the allocator.

On the user side, sbrk() now takes two flag bits: SBRK_LAZY (allocate on page fault instead of immediately) and SBRK_SUPER (use 2MB pages). They can be combined freely.

Copy-on-write

With reference counts in place, fork() no longer copies page contents.

uvmcopy() shares the parent's pages with the child. It clears PTE_W, sets PTE_RSW if the page was writable, and increments the reference count: 

// kernel/vm.c, uvmcopy()
if(*pte & PTE_W)
  *pte = (*pte & ~PTE_W) | PTE_RSW;
*new_pte = *pte;
kaddrefcnt((void *)PTE2PA(*pte));

Known limitations

  • One global lock. The next step is per-CPU free lists, with the global lock kept only for the shared superpage pool.
  • Only level-0 page-table pages are freed on unmap. Empty level-1 tables stay allocated. With 128MB of RAM, a process cannot grow large enough for this to matter, but it would if PHYSTOP grew. (Why uvmunmap() frees empty tables at all is explained in the debugging page.)
  • Coalescing is immediate. A group is merged back as soon as its 512th page is freed. A workload that repeatedly frees and allocates pages in one group would split and merge it over and over.
