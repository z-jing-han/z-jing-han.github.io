xv6-riscv · Debugging

Debugging a merged kernel

Rebuilding the physical memory allocator broke things. The two failures that took the longest to find both turned out to sit outside the code I had just written — one in a page-mapping loop that had been quietly wrong for years, one in how the test measured free memory rather than in the memory itself.

GDB · QEMU kernel/vm.c, kernel/proc.c Aug 2026 MIT 6.1810, self-study

In short

New code is the first place to look, and both times it was the wrong place. Ruling out the new allocator cheaply — with assertions that already existed — is what made it reasonable to go looking further afield, at a page-mapping off-by-one reachable only by a workload that uses memory out to the physical limit, and at a leak that a purpose-built diagnostic proved was never a leak at all.

A third group of bugs came from the merge itself: state that was correct while one lab owned it, and wrong once five labs shared one struct proc and one allocator. Those are invisible from inside any single lab.

01 · Bug one

Two bugs that masked each other

The symptom pointed straight at the newest code. The cause was an off-by-one in mappages() — a function the refactor never touched — and fixing it exposed a second, independent bug that the first one had been hiding.

Symptom

usertests -q and pgtbltest panicked almost immediately at boot with kerneltrap, scause=0xf (store page fault), and stval landing reliably at PHYSTOP - PGSIZE — the very top page of physical memory.

Ruling out

The new coalescing and reference-counting logic was the first suspect, because new code usually is. The allocator's three internal assertions — a page's count must be 0 before its group coalesces, plus bounds checks on the per-group free counter in both directions — never fired, which ruled that out with high confidence at nearly zero cost.

That justified going further afield, with GDB: break at the faulting sepc, info symbol to resolve it to split_locked(), disassemble /s to confirm the exact instruction, and x/4xg on the faulting address to establish directly that the kernel page table had no mapping there at all.

Root cause

mappages() advanced the address and then tested whether it had reached the end of the range, so the final page of any range was never mapped: 

*pte = PA2PTE(pa) | perm | PTE_V;
a += PGSIZE;
if(a >= last) break;      // last page of the range: never mapped

Every other call site maps a single page per call, where the dropped page is the only page and the failure would have been obvious. The one call that maps a huge, nearly system-wide range is kvmmake() at boot — and the page it quietly dropped was exactly the top of physical memory. The allocator was right that the page was free; the kernel page table had simply never mapped it since boot.

Fix

Test for the end of the range before stepping, so the final page is mapped:

*pte = PA2PTE(pa) | perm | PTE_V;
if(a >= last) break;
a += step;
pa += step;

The fix changed the symptom instead of removing it

Fixing the loop order flipped the failure into panic: mappages: remap. The range-end calculation had hardcoded PGSIZE regardless of whether the call was stepping by PGSIZE or SUPERPGSIZE: 

last = va + size - PGSIZE;   // wrong when the step is a superpage
int L = (((super == 1) && (size >= SUPERPGSIZE)) ? 1 : 0);
uint64 step = (L == 1) ? SUPERPGSIZE : PGSIZE;
last = va + size - step;

Under the old loop order these two errors cancelled out. Fixing only the first made a single superpage-sized call overrun its range by one page's worth of address space — straight into memory the next iteration was about to map, hence remap.

The takeaway: two bugs that mask each other are the most dangerous kind, because a fix that changes the symptom instead of removing it looks like progress. That is the signal to go looking for a second, independent cause — not to start guessing at a third. It is also why this was not treated as finished until the whole of pgtbltest and usertests -q ran clean again, rather than just the one case that had originally failed.

02 · Bug two

The books were right; the yardstick was wrong

A leak that survived every fix, by a small and suspiciously stable amount. What cracked it was building a second, independent way to ask the same question.

Symptom

usertests -q consistently reported "lost some free pages" by a small, stable count — regardless of whether coalescing was enabled, and regardless of which earlier bug had already been fixed.

Ruling out

Two suspects went first: the process cleanup path failing to free trapframe/usys/handframe, and the allocator's own bookkeeping. Printing those pointers in allocproc() and freeproc() confirmed every kfree() happened as expected.

Then the turning point: a purpose-built diagnostic, kfreecount(), walked the allocator's two freelists directly and counted them — bypassing sbrk() and the entire syscall and page-table path that the test itself uses to measure free memory. Its number was correct at every step, which meant the leak was not in the allocator at all. It was somewhere between the allocator and the way free memory was being measured.

Root cause

The measurement grows a process's heap until memory runs out, then shrinks it back in one call. Growing allocates data pages and the intermediate page-table pages that walk() creates on demand. Shrinking only ever unmapped and freed the leaf data pages — the now-completely-empty intermediate page-table pages were never reclaimed, and stayed allocated until the process exited. That grow-then-shrink pattern repeats throughout the run, so abandoned tables accumulated.

Fix

Extend uvmunmap()'s table trimming — which previously handled only the last 2MB region, and only cleared PTEs without freeing the table page itself — to check, for every 2MB region the unmap touches, whether that page-table page is now entirely empty, and if so actually kfree() it and clear the parent PTE. 

// kernel/vm.c — uvmunmap(), after the unmap loop
for(uint64 region = va - (va % SUPERPGSIZE); region < va + npages*PGSIZE; region += SUPERPGSIZE){
  pte = walk(pagetable, region, 0, 1);
  /* skip missing, invalid, or superpage-leaf entries */
  pte_t *tbl = (pte_t *)PTE2PA(*pte);
  int empty = 1;
  for(int i = 0; i < PGS_PER_SUPER && empty == 1; i++)
    if(tbl[i] & PTE_V)
      empty = 0;
  if(empty){
    kfree((void*)tbl);
    *pte = 0;
  }
}

The generalisable part: when a number reported through one path disagrees with reality, build an independent lower-level way to ask the same question instead of re-reading the same code. kfreecount() existed for exactly that, and it separated "allocator problem" from "measurement problem" in minutes rather than hours.

03 · Bug three, six times

The bugs only a merged kernel can have

A last round of failures showed up in usertests only under particular conditions. Five of the six are the same species: state that was perfectly correct while one lab owned it, and wrong once five labs share one struct proc and one allocator.

A superpage freed through the 4KB door

cowfault() dropped its old reference with a plain kfree() even when the PTE was a 2MB leaf. The allocator's uniform reference counting only holds if callers pick the matching granularity, so the fix is a one-liner (super ? superfree(pa) : kfree(pa)) for a class of bug that is anything but: the accounting stays self-consistent while silently describing the wrong frame.

A 32-bit shift for a 64-entry mask

The sandbox's reject mask was an int, tested with 1 << num. Syscall numbers run past 31, which makes that shift undefined behaviour and the wrong bit either way. Fixed to uint64 with 1UL << num and an explicit num >= 64 bound — the bound being the part that keeps it correct when the syscall table grows again.

A copy that dropped its terminator

Carrying the sandbox's allowed path across fork() was written as strncpy(dst, src, strlen(src)) — which copies exactly the characters and not the trailing NUL, so the child's path ran into whatever followed it in memory. Replaced with safestrcpy(dst, src, sizeof(dst)). The first attempt at the fix was itself the bug, which is its own argument for bounding by the destination's size rather than the source's length.

Timer-handler state surviving process reuse

The alarm lab's per-process fields (ticks, handler, in_handler) were neither cleared by kexec() nor reset in freeproc(), so a recycled struct proc could inherit a previous process's timer handler — and the page-table lab's shared usys page needed its pid set at allocation time for the same reason. Process reuse is a lifecycle no single lab exercises hard enough to notice.

A backtrace walking away from its stack

The frame-pointer walk was bounded with PGROUNDDOWN(fp) and looped while fp >= bound. The chain climbs toward the top of the stack page, so it has to be bounded by PGROUNDUP(fp) and run while fp < bound. Walking the right structure in the wrong direction still terminates — it just prints garbage first, which is why it survived until something else went wrong and the backtrace was needed.

One lab's deliberate exception, applied to only half the code

Freed memory is filled with junk to catch dangling references, except when the attack exercise needs to observe stale data — a switch that was honoured in kfree() but missing from superfree(). Whether the exception applied depended on which granularity happened to back the page, which is the kind of inconsistency that makes a test flaky rather than failing.

None of these are visible from inside a single lab, and none of them are allocator bugs. They are the actual cost of running five labs' features at once, and they are the reason "all five suites still run clean" is the bar I hold the merged kernel to rather than "each lab passed when I wrote it".

04 · Method

What carried from bug to bug

Six habits that did the actual work, in rough order of how early they pay off.

  • 01 Read what the hardware already told you. On RISC-V, scause, stval and sepc narrow the search space before you write a single line of debug code.
  • 02 Turn silent corruption into a locatable panic. Cheap invariants caught neither headline bug directly — but ruling out a whole class of suspect for a few assertions is a good trade every time.
  • 03 When reasoning stalls, ask the running system. break, info symbol, disassemble /s and x/4xg settled the mappages() bug that reading the source had not.
  • 04 Question the measurement, not just the system measured. A purpose-built kfreecount() existed only to tell those two possibilities apart.
  • 05 Bisect with a switch, not a guess. Disabling coalescing and re-running halved the suspect list before GDB was needed at all.
  • 06 Re-run everything after any fix. Bug one's second, independent cause only became visible after the first was fixed.
