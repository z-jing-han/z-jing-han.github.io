Debugging the merged kernel

After the allocator rewrite, two bugs took most of the debugging time. Neither was in the new allocator. One was in my earlier superpage change to mappages(), and the other was in how the test measured free memory. This page also lists six smaller bugs caused by the merge.

GDB · QEMU Aug 2026

Bug 1: two bugs hiding each other

Symptom

usertests -q and pgtbltest panicked right after boot: kerneltrap with scause=0xf (store page fault) and stval equal to PHYSTOP - PGSIZE, the top page of physical memory.

Investigation

I suspected the new allocator first, but none of its assertions fired. In GDB I set a breakpoint at the faulting sepc, used info symbol to see that it was in split_locked(), checked the instruction with disassemble /s, and used x/4xg to confirm that the kernel page table had no mapping for that address.

Root cause

Three weeks earlier, when I added superpage support to mappages() in the page-table lab, I changed the loop to advance the address before checking for the end of the range. Stock xv6 checks first. As a result, the last page of every multi-page 4KB range was not mapped: 

*pte = PA2PTE(pa) | perm | PTE_V;
a += PGSIZE;
if(a >= last) break;      // the last page is never mapped

Single-page calls still worked, because the first page is mapped before the check. However, kvmmake() maps all kernel RAM as one range at boot, so the top page of memory was never mapped. The problem only showed up once the new allocator handed that page out.

Fix

Check for the end of the range before advancing:

*pte = PA2PTE(pa) | perm | PTE_V;
if(a >= last) break;
a += step;
pa += step;

The fix exposed a second bug

After the fix, boot failed with panic: mappages: remap. The end address was still computed with PGSIZE, even when the loop steps by 2MB: 

last = va + size - PGSIZE;   // wrong when stepping by SUPERPGSIZE
int L = (((super == 1) && (size >= SUPERPGSIZE)) ? 1 : 0);
uint64 step = (L == 1) ? SUPERPGSIZE : PGSIZE;
last = va + size - step;

With the old loop order, this mistake had no effect on superpage mappings. With the new order, a superpage mapping went one step past the end of its range and hit an existing mapping. After fixing both, I re-ran all of pgtbltest and usertests -q, not only the test that had failed.

Bug 2: a leak that was a measurement problem

Symptom

usertests -q reported "lost some free pages" by a small number that stayed the same across runs, with or without coalescing enabled.

Investigation

I first checked whether freeproc() freed the trapframe, usys and handframe pages by printing them in allocproc() and freeproc(). It did.

Then I wrote a temporary function, kfreecount() (not committed), that counts both free lists directly instead of measuring through sbrk() like the test does. Its count was always correct, so the allocator was not losing pages. The difference had to come from the way the test measured free memory.

Root cause

The test grows a process's heap until memory runs out, then shrinks it again. Growing allocates data pages and also the page-table pages created by walk(). Shrinking freed the data pages but left the now-empty page-table pages allocated until the process exited. The test does this many times, so the empty tables added up.

Fix

After unmapping, uvmunmap() checks each 2MB region it touched and frees the level-0 page-table page if it has no valid entries left. Before this change, it only handled the last region and did not free the table page itself. 

// kernel/vm.c, end of uvmunmap()
for(uint64 region = va - (va % SUPERPGSIZE); region < va + npages*PGSIZE; region += SUPERPGSIZE){
  pte = walk(pagetable, region, 0, 1);
  /* skip missing, invalid, or superpage entries */
  pte_t *tbl = (pte_t *)PTE2PA(*pte);
  int empty = 1;
  for(int i = 0; i < PGS_PER_SUPER && empty == 1; i++)
    if(tbl[i] & PTE_V)
      empty = 0;
  if(empty){
    kfree((void*)tbl);
    *pte = 0;
  }
}

Six bugs caused by the merge

These showed up in usertests under specific conditions and were fixed in the last three commits. Most of them were correct while one lab owned the code, and broke once all five labs shared struct proc and the allocator.

A superpage freed as a 4KB page

cowfault() always released the old page with kfree(), even for a 2MB mapping. It now calls superfree() for superpages.

A syscall mask that was too small

The sandbox mask was an int tested with 1 << num, but syscall numbers go up to 35. I changed it to uint64 with 1UL << num and added a num >= 64 check.

A path copied without its terminator

fork() copied the allowed path with strncpy(dst, src, strlen(src)), which does not copy the '\0'. That line was my own first attempt at a fix. The final version uses safestrcpy(dst, src, sizeof(dst)).

Alarm state kept after process reuse

The alarm fields (ticks, handler, in_handler) were not reset in kexec() or freeproc(), so a new process in a reused struct proc could inherit the previous handler. For the same reason, the pid in the usyscall page now has to be set when a process is allocated.

A backtrace walking the wrong way

The loop was bounded by PGROUNDDOWN(fp) and ran while fp >= bound. Saved frames move toward the top of the stack page, so it should use PGROUNDUP(fp) and fp < bound.

A switch applied to only one free function

kfree() skipped the junk fill when LAB_SYSCALL is defined, because the attack test needs to see old data, but superfree() did not. Whether attack could see the old data depended on which page size backed the memory.

What helped most

  1. Reading scause, stval and sepc first. They narrowed down where to look before I added any debug code.
  2. Keeping simple assertions in new code, so I could rule it out quickly.
  3. Using GDB on the running kernel when reading the source did not explain the failure.
  4. Measuring a suspicious number a second way (kfreecount()) instead of re-reading the same code.
  5. Turning coalescing off to cut down the list of suspects.
  6. Re-running every test after each fix. The second mappages() bug only appeared after the first one was fixed.
