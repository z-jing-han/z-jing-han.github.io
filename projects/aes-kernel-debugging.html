AES Linux Kernel Module · Design & Debugging

Debugging a double-free in a streaming crypto device

A kernel module that streams AES-ECB encryption through a character device has to make two things agree: a cipher that only understands 16-byte blocks, and a read()/write() interface that promises neither size nor alignment. Getting that streaming design right is what surfaced a double-free that only panicked under concurrent load — inherited almost unchanged from four lines of code the course staff handed out.

C · Linux Kernel Crypto API todo/cryptomod/cryptomod.c Spring 2025 NYCU APUE, Lab 02

In short

cryptomod.c implements /dev/cryptodev, a per-file-descriptor AES-ECB crypto device configured over ioctl, with an ADV I/O mode that encrypts or decrypts incrementally as bytes arrive instead of waiting to see the whole payload.

This page covers the two things the project-card bullets don't have room for: why ADV-mode decryption always keeps one block sitting in the buffer, and a kernel panic that looked like a multi-threading race — fixed by adding printk() calls, which made it worse, not better — until it was traced to a kfree() that was correct in the code it was copied from and wrong the moment it was copied.

01 · Interface

One buffer, one state machine, per file descriptor

The spec requires every opened file descriptor to carry its own encryption state, so the module reaches for the same buffer on every write(), read() and ioctl() against that fd, and never touches another fd's.

cryptomod_dev_open() kmallocs a small struct cryptomod_data plus a 4096-byte kernel_buffer, and hands both off through file->private_data; cryptomod_dev_close() frees them back in reverse (cryptomod.c:49–79). That allocate-once, free-once pairing is exactly the ownership contract the bug in section 03 ends up breaking. 

// cryptomod.c
struct cryptomod_data {
    pid_t pid;
    char* kernel_buffer;              // owned by open()/close(), nothing else
    size_t cur_kernel_buffer_pos;
    struct CryptoSetup crypto_config; // key, key_len, io_mode, c_mode
    int device_setup;
    int finalize;
};

The four ioctl commands are the state machine's only transitions:

  • CM_IOC_SETUPValidates key length and mode, resets the buffer position, zeroes the buffer.
  • CM_IOC_FINALIZEApplies or validates PKCS#7 padding — the only place padding is decided.
  • CM_IOC_CLEANUPResets position and buffer contents, clears the finalize flag, keeps the fd open.
  • CM_IOC_CNT_RSTResets the global byte counters and frequency table, under global_lock.

02 · The design

Why ADV mode always keeps one block back

PKCS#7 padding is only decided when the caller signals end-of-stream with CM_IOC_FINALIZE. Handing back the last available block before that point risks handing back padding — and read() can't take bytes back once they've crossed into user space.

In ADV mode, every read() decrypts and returns whatever full blocks are sitting in the buffer immediately — that's the whole point of streaming instead of buffering the entire payload like BASIC mode does. It's safe for every block except the last one, and nothing in a single read() call can tell whether the block it's about to hand back is the last one. 

// cryptomod.c:166-170 — keep at least a block in dev for padding
size_t process_bytes = min(len - len % CM_BLOCK_SIZE,
    data->cur_kernel_buffer_pos - data->cur_kernel_buffer_pos % CM_BLOCK_SIZE);
if (data->crypto_config.io_mode == ADV && data->crypto_config.c_mode == DEC &&
    !data->finalize && data->cur_kernel_buffer_pos - process_bytes < CM_BLOCK_SIZE) {
    process_bytes -= CM_BLOCK_SIZE;
}

process_bytes first rounds down to whole blocks, then — only for ADV+DEC, only before finalize — gives one block back if that would otherwise empty the buffer. The result: exactly one block is always left waiting when CM_IOC_FINALIZE arrives.

Trade-off: withholding bounds the cost to at most one block (16 bytes) per fd, at the price of one extra branch on every ADV+DEC read. BASIC mode sidesteps the question entirely by not processing anything until FINALIZE — simpler, but it buffers the whole payload instead of streaming it, up to the fd's 4096-byte limit.

03 · Debugging

A double-free inherited from four lines of given code

The panic only showed up under the multi-threaded stress test, and adding a printk() at the top and bottom of a function made it disappear — which reads like a timing-sensitive race condition. It wasn't one.

Symptom

cryptomod.ko panicked intermittently under test_crypto's concurrent workload. The failure moved around from run to run, and got conspicuously harder to reproduce whenever printk() calls were added near the crypto path — the kind of symptom that points straight at a data race.

Ruling out

The obvious suspects were the globals every thread actually shares: byte_read, byte_write and the 256-entry frequency table. All three are only ever touched inside global_lock (cryptomod.c:153–155, 184–187, 195–197, 285–289) — correctly locked, every access. That ruled out a visibility race on shared state and left a narrower, less obvious question: not whether two threads could see stale data, but whether one thread's per-fd buffer could stop being valid memory in the first place.

Root cause

The course staff's given sample_code.c allocates its own scratch buffer inside test_skcipher() and frees it on the way out — correct, because the function owns that allocation: 

// spec/sample_code.c:45,78 — given reference code
data = kmalloc(datasize, GFP_KERNEL);  // local to this function
/* ...encrypt in place... */
out:
    crypto_free_skcipher(tfm);
    skcipher_request_free(req);
    kfree(data);                       // correct: frees what it just allocated

Adapting it into cryptomod.c meant swapping that local buffer for the fd's persistent one — data = private_data->kernel_buffer (cryptomod.c:85), the same buffer open() allocates once and close() frees once. The given code's trailing kfree() came along for the ride: 

// cryptomod.c — test_skcipher(), as first adapted
u8* data = private_data->kernel_buffer;  // now points at the fd's persistent buffer
/* ...encrypt or decrypt in place... */
out:
    crypto_free_skcipher(tfm);
    skcipher_request_free(req);
    kfree(data);                         // frees a buffer this function does not own

test_skcipher() runs on nearly every read() in ADV mode (cryptomod.c:180). The first call frees kernel_buffer while read() still dereferences it two lines later to satisfy copy_to_user(); every following write() or read() on that fd then operates on freed memory; and cryptomod_dev_close() frees the same pointer a second time when the fd is released. A single misplaced kfree() produces both an immediate use-after-free and an eventual double-free.

That also explains the printk() clue. printk() serializes through the kernel console's internal lock and is comparatively slow, which shifts the allocator's timing just enough that the freed buffer usually wasn't reused — and corrupted — inside the narrow window before the code touched it again. The symptom got rarer, not gone: a classic use-after-free heisenbug, not evidence of a race the lock was missing.

Fix

Delete the inherited kfree() entirely. kernel_buffer's lifetime belongs exclusively to cryptomod_dev_open() and cryptomod_dev_close() — the same allocate-once, free-once discipline the given code followed correctly, restored once test_skcipher() stopped freeing a buffer it was only ever supposed to borrow (cryptomod.c:128–133).

The given code wasn't wrong — it was correct for a buffer it owned outright. The bug is what happens when that assumption travels silently into code where the same pointer is borrowed, not owned.

04 · Method

What this bug actually confirmed

Four habits, in the order they mattered.

  • 01 Ownership travels with scope, not with code that was correct elsewhere. The given kfree() was right where it was written; it stopped being right the instant the pointer's lifetime changed from function-local to per-fd.
  • 02 A fix that changes a bug's odds isn't a fix. Adding printk() made the panic rarer, not absent — a shift in probability is a reason to keep digging, not a reason to stop.
  • 03 Match every kmalloc to exactly one kfree, on paper. Tracing kernel_buffer's single intended owner was enough to spot the second, uninvited one.
  • 04 A "race condition" hypothesis should survive an actual concurrency check. The real trigger needed zero concurrent threads; the stress test only made it more likely to land inside the corruption window.
