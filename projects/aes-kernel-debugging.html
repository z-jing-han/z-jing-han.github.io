AES Linux Kernel Module · Design & Debugging

Debugging a double-free in a streaming crypto device

A kernel module that streams AES-ECB encryption through /dev/cryptodev, configured over ioctl. Under concurrent load it returned wrong output, traced back to a single kfree() copied from course-provided sample code.

C · Linux Kernel Crypto API cryptomod.c Spring 2025

In short

cryptomod.c implements /dev/cryptodev, a per-file-descriptor AES-ECB crypto device configured over ioctl, with an ADV I/O mode that encrypts or decrypts incrementally as bytes arrive instead of waiting to see the whole payload.

This page covers three things the project-card bullets don't have room for: a double-free that surfaced under concurrent load as wrong decrypted output, traced with the kernel's slab-allocator debug checks; a second gap the same fix left open — several threads sharing one fd; and, at the end, the block-withholding design behind ADV-mode decryption.

16/24/32 Byte key lengths supported (AES-128/192/256)
4096 Byte kernel buffer, owned per open file descriptor
2 I/O modes sharing that one buffer
1 Inherited kfree() behind the double-free

01 · Interface

One buffer, one state machine, per file descriptor

Every opened file descriptor carries its own encryption state, so the module reaches for the same buffer on every write(), read() and ioctl() against that fd, and never touches another fd's.

cryptomod_dev_open() kmallocs a small struct cryptomod_data plus a 4096-byte kernel_buffer, and hands both off through file->private_data; cryptomod_dev_close() frees them back in reverse (cryptomod.c:50–82). That allocate-once, free-once pairing is exactly the ownership contract the bug in section 02 ends up breaking — and the reason fd_lock in section 03 is initialized and destroyed right alongside it. 

// cryptomod.c
struct cryptomod_data {
    pid_t pid;
    char* kernel_buffer;              // owned by open()/close(), nothing else
    size_t cur_kernel_buffer_pos;
    struct CryptoSetup crypto_config; // key, key_len, io_mode, c_mode
    int device_setup;
    int finalize;
    struct mutex fd_lock;             // serializes read()/write()/ioctl() on this fd
};

The four ioctl commands are the state machine's only transitions:

  • CM_IOC_SETUPValidates key length (16, 24, or 32 bytes — AES-128/192/256) and mode, resets the buffer position, zeroes the buffer.
  • CM_IOC_FINALIZEApplies or validates PKCS#7 padding — the only place padding is decided.
  • CM_IOC_CLEANUPResets position and buffer contents, clears the finalize flag, keeps the fd open.
  • CM_IOC_CNT_RSTResets the global byte counters and frequency table, under global_lock.

02 · Debugging

Wrong output under load, traced to a double-free

Under concurrent load, decrypted output sometimes came back wrong, and adding printk() calls made the problem disappear — which looks like a timing-sensitive race, but the cause was a memory-ownership bug.

Symptom

With multiple threads running, the encrypted or decrypted results a user program received from the device were wrong; single-threaded runs were always correct. Adding a printk() at the top of read(), write(), and ioctl() made the multi-threaded results correct again. Separately, roughly 1 run in 20, under any configuration, printed a panic-like kernel warning that didn't stop the system, and its reported location had no obvious connection to the AES module.

Investigation

To make the problem observable, multi_test.c — a reproduction test written for this bug — forks several processes that each open /dev/cryptodev independently and use their own PID as the plaintext, so every process's data is distinguishable. Its output showed that roughly half the time, a process's kernel buffer held another PID's plaintext or ciphertext instead of its own — pointing to memory being reused across allocations that should have been independent.

To inspect the memory state directly, QEMU was booted with SLUB debugging enabled (slub_debug=FZUP) and a run was captured in double-kfree.log. The log contains Slab has 0 allocated objects but 1 are to be freed, which indicates a double free. Searching the log for multi_test and following the panic call stack below it shows the failure occurring in test_skcipher().

Root cause

The course staff's given sample_code.c allocates its own scratch buffer inside test_skcipher() and frees it on the way out — correct, because the function owns that allocation: 

// sample_code.c:45,78 — course-provided reference code
data = kmalloc(datasize, GFP_KERNEL);  // local to this function
/* ...encrypt in place... */
out:
    crypto_free_skcipher(tfm);
    skcipher_request_free(req);
    kfree(data);                       // correct: frees what it just allocated

Adapting it into cryptomod.c meant swapping that local buffer for the fd's persistent one — data = private_data->kernel_buffer (cryptomod.c:88), the same buffer open() allocates once and close() frees once. The given code's trailing kfree() came along for the ride: 

// cryptomod.c — test_skcipher(), as first adapted
u8* data = private_data->kernel_buffer;  // now points at the fd's persistent buffer
/* ...encrypt or decrypt in place... */
out:
    crypto_free_skcipher(tfm);
    skcipher_request_free(req);
    kfree(data);                         // frees a buffer this function does not own

test_skcipher() runs on nearly every read() in ADV mode (cryptomod.c:201). Freeing kernel_buffer there hands that memory back to the slab allocator's free list, and the very next unrelated kmalloc() anywhere in the kernel, including another process's cryptomod_dev_open(), is free to reuse that exact block. Once two file descriptors' private_data->kernel_buffer point at the same memory, each process's read()/write() overwrites what the other is still using, which shows up as one process's output containing another's bytes. Most of the time the memory is simply reused; only occasionally does the allocator's debug check notice the double free and print the panic-like warning seen in the symptom.

That also accounts for the printk() observation. printk() is comparatively slow and serializes through the console lock, which shifts allocator timing enough that a process's next allocation usually didn't land on the block it had just mistakenly freed before that process touched it again — so the wrong output stopped appearing even though the bug was still there.

Fix

Take out the inherited kfree() (cryptomod.c:131–136). Removing that one call turned out to be the easy part; auditing a different sharing pattern it didn't cover is section 03.

03 · Hardening

A different sharing pattern the first fix didn't cover

multi_test.c's processes each open their own fd, so every kernel_buffer is private to one file descriptor — fixing the double-free closes that path completely for it. That leaves a different pattern: one fd shared by several threads. Nothing in the module serialized read()/write()/ioctl() calls landing on the same open file descriptor at once.

share_fd_test.c opens /dev/cryptodev once, then spawns several threads that all call write() on that single shared fd at once, each writing one 16-byte block tagged with its own signature byte. CM_IOC_SETUP runs once, single-threaded, before any thread starts, so the test isolates exactly one thing: the internal race in cryptomod_dev_write() on cur_kernel_buffer_pos. After CM_IOC_FINALIZE and a decrypt round-trip, it checks that no 16-byte window mixes two threads' bytes and that every thread's signature shows up exactly once. 

// cryptomod.c — write(), before fd_lock existed
size_t process_bytes = min(len, MAX_BUFFER_SIZE - data->cur_kernel_buffer_pos);
copy_from_user(data->kernel_buffer + data->cur_kernel_buffer_pos, buf, process_bytes);
data->cur_kernel_buffer_pos += process_bytes;  // read-modify-write, no lock

Two threads landing between the read and the write of cur_kernel_buffer_pos can compute the same destination offset, so one thread's copy_from_user() silently overwrites bytes the other just placed — exactly the torn or missing chunks share_fd_test.c checks for. 

// cryptomod.c:143-172 — write(), now single-entry / single-exit under fd_lock
    mutex_lock(&data->fd_lock);
    /* ...validate, copy_from_user, advance cur_kernel_buffer_pos... */
    mutex_unlock(&data->fd_lock);
    return process_bytes;

write_err:
    mutex_unlock(&data->fd_lock);
    return err;

read() (cryptomod.c:175–227) and ioctl() (cryptomod.c:230–346) follow the same shape: take fd_lock on entry and release it on every path out, with error paths funneling through one labeled exit. fd_lock itself lives in struct cryptomod_data (cryptomod.c:37), initialized in open() and destroyed in close() (cryptomod.c:65, 77) — the same lifecycle as the buffer it now guards.

04 · The design

Why ADV mode always keeps one block back

PKCS#7 padding is only decided when the caller signals end-of-stream with CM_IOC_FINALIZE. Handing back the last available block before that point risks handing back padding — and read() can't take bytes back once they've crossed into user space.

In ADV mode, every read() decrypts and returns whatever full blocks are sitting in the buffer immediately — that's the whole point of streaming instead of buffering the entire payload like BASIC mode does. It's safe for every block except the last one, and nothing in a single read() call can tell whether the block it's about to hand back is the last one. 

// cryptomod.c:186-190 — keep at least a block in dev for padding
size_t process_bytes = min(len - len % CM_BLOCK_SIZE,
    data->cur_kernel_buffer_pos - data->cur_kernel_buffer_pos % CM_BLOCK_SIZE);
if (data->crypto_config.io_mode == ADV && data->crypto_config.c_mode == DEC &&
    !data->finalize && data->cur_kernel_buffer_pos - process_bytes < CM_BLOCK_SIZE) {
    process_bytes -= CM_BLOCK_SIZE;
}

process_bytes first rounds down to whole blocks, then — only for ADV+DEC, only before finalize — gives one block back if that would otherwise empty the buffer. The result: exactly one block is always left waiting when CM_IOC_FINALIZE arrives.
