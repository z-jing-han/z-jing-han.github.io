Debugging a double-free in a kernel crypto module

cryptomod is a Linux kernel module that provides AES-ECB encryption through /dev/cryptodev, configured with ioctl. Under concurrent load, processes sometimes read back another process's data. The cause was a kfree() I had copied from the course sample code.

C · Linux crypto API · QEMU Spring 2025 · fixed Oct 2025 · traced Sep 2026

The interface

The device interface is defined by the lab spec. Each open() allocates a struct cryptomod_data and a 4096-byte buffer and stores them in file->private_data. close() frees both (cryptomod.c:50–82). 

// cryptomod.c:30-38
struct cryptomod_data {
    pid_t pid;
    char* kernel_buffer;              // allocated in open(), freed in close()
    size_t cur_kernel_buffer_pos;
    struct CryptoSetup crypto_config; // key, key_len, io_mode, c_mode
    int device_setup;
    int finalize;
    struct mutex fd_lock;             // added later, see below
};
  • CM_IOC_SETUP checks the key length (16, 24 or 32 bytes) and the modes, and clears the buffer.
  • CM_IOC_FINALIZE adds PKCS#7 padding when encrypting, or checks and removes it when decrypting.
  • CM_IOC_CLEANUP clears the buffer and the finalize flag.
  • CM_IOC_CNT_RST resets the global byte counters and byte-frequency table shown in /proc/cryptomod.

The double-free

Symptom

With several threads or processes, the encrypted or decrypted output was sometimes wrong. Single-threaded runs were always correct. Adding printk() at the start of read(), write() and ioctl() made the problem go away. About one run in twenty also printed a kernel warning that pointed to code unrelated to the module.

Investigation

I wrote multi_test.c, which forks several processes that each open /dev/cryptodev and use their own PID as the plaintext, so it is clear whose data ends up where. In about half of the runs, a process read back another PID's data.

I then booted QEMU with slub_debug=FZUP and saved the output in double-kfree.log. It reports Slab has 0 allocated objects but 1 are to be freed, which is a double free, and the call stack for multi_test goes through test_skcipher().

Root cause

The course's sample_code.c allocates a buffer in test_skcipher() and frees it at the end, which is correct there: 

// sample_code.c:45,78 (course sample code)
data = kmalloc(datasize, GFP_KERNEL);
/* ... encrypt in place ... */
out:
    crypto_free_skcipher(tfm);
    skcipher_request_free(req);
    kfree(data);

In cryptomod.c I changed data to point to the fd's buffer, which open() allocates and close() frees, but I kept the kfree(): 

// cryptomod.c, test_skcipher(), first version
u8* data = private_data->kernel_buffer;
/* ... encrypt or decrypt in place ... */
out:
    crypto_free_skcipher(tfm);
    skcipher_request_free(req);
    kfree(data);                  // frees the fd's buffer while it is still in use

test_skcipher() runs on almost every read() (cryptomod.c:201), so the buffer was returned to the slab allocator while the fd was still using it. The next kmalloc() of the same size, for example another process's open(), could get the same memory, and then two fds shared one buffer. close() later freed it a second time. The printk() calls changed the timing so that the memory was reused less often, which is why they hid the bug.

Fix

Remove the kfree() (cryptomod.c:131–136). That part was easy, but it raised another question: multi_test.c only covers processes with their own fd, so what happens when several threads share one fd? That is the next section.

Several threads on one fd

Nothing stopped two threads' write() calls on the same fd from reading the same cur_kernel_buffer_pos and copying their data to the same place: 

// cryptomod.c, write() before fd_lock
copy_from_user(data->kernel_buffer + data->cur_kernel_buffer_pos, buf, process_bytes);
data->cur_kernel_buffer_pos += process_bytes;  // not atomic

I wrote share_fd_test.c, in which several threads write ID-tagged 16-byte blocks to one fd and then check that each block comes back once and unmixed. To fix the race, I added a per-fd mutex, fd_lock, that read(), write() and ioctl() hold for their whole duration (cryptomod.c:143–346). The global counters in /proc/cryptomod use a separate global mutex.

Why ADV decryption keeps one block

PKCS#7 padding is only known at CM_IOC_FINALIZE. In ADV decrypt mode, read() returns complete blocks as soon as they are available. The last block may contain padding, and bytes already returned to user space cannot be taken back. So before FINALIZE, read() always leaves at least one block in the buffer: 

// cryptomod.c:186-190
size_t process_bytes = min(len - len % CM_BLOCK_SIZE,
    data->cur_kernel_buffer_pos - data->cur_kernel_buffer_pos % CM_BLOCK_SIZE);
if (data->crypto_config.io_mode == ADV && data->crypto_config.c_mode == DEC &&
    !data->finalize && data->cur_kernel_buffer_pos - process_bytes < CM_BLOCK_SIZE) {
    process_bytes -= CM_BLOCK_SIZE;
}
